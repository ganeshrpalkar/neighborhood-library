Concurrency & Row Locking

The race condition, the fix, and why this is your strongest architectural story for the interview.

The Problem — A Race Condition

Suppose exactly one copy of Dune is available. Two staff members try to borrow it for different members at the same instant. Without concurrency control:

Request A                         Request B
─────────────────────────────────────────────────────────
SELECT available_copies → 1       SELECT available_copies → 1
copies >= 1?  YES                 copies >= 1?  YES
available_copies -= 1             available_copies -= 1
INSERT loan for member 7          INSERT loan for member 9
COMMIT  (copies = 0)              COMMIT  (copies = -1)  ❌

Both transactions read available_copies = 1 before either one commits. Both proceed. The result: two active loans for one physical book and a negative inventory count — a data integrity violation.

This is a classic lost update: two reads interleave before either write, so each transaction acts on stale data.

The Fix — Pessimistic Row Locking

The solution is to lock the book row at read time. PostgreSQL's SELECT … FOR UPDATE says: "I'm reading this row and I intend to modify it — hold an exclusive row lock until I commit or rollback."

Request A                         Request B
─────────────────────────────────────────────────────────
SELECT … FOR UPDATE  → lock ✓
                                  SELECT … FOR UPDATE  → WAITS 🔒
available_copies = 1  → OK
available_copies = 0
INSERT loan for member 7
COMMIT  → lock released
                                  lock acquired
                                  available_copies = 0
                                  copies >= 1?  NO  → 409 ConflictError

Request B queues behind Request A. By the time it acquires the lock the count is already 0, and it correctly rejects the borrow with a 409.

The Code — borrow_book

In app/api/v1/loans/services.py:

def borrow_book(
    db: Session, book_id: int, member_id: int,
    due_date: datetime | None = None,
) -> Loan:

    # Lock the book row — concurrent borrows of the same book queue here
    book = db.scalars(
        select(Book).where(Book.id == book_id).with_for_update()
    ).first()

    if book is None:
        raise NotFoundError(f"Book {book_id} not found")

    member = db.get(Member, member_id)
    if member is None:
        raise NotFoundError(f"Member {member_id} not found")

    # Safe to check — we own the row lock
    if book.available_copies < 1:
        raise ConflictError(f"'{book.title}' has no available copies")

    # Both mutations in one transaction
    book.available_copies -= 1
    loan = Loan(
        book_id=book_id,
        member_id=member_id,
        due_date=due_date or (_now() + timedelta(days=settings.LOAN_PERIOD_DAYS)),
        status="active",
        fine_amount=0,
    )
    db.add(loan)

    try:
        db.commit()              # book update + loan insert commit together
    except IntegrityError:       # defense-in-depth: DB constraint violated
        db.rollback()
        raise ConflictError(f"'{book.title}' has no available copies")

    db.refresh(loan)
    return loan

The Code — return_loan (Double Lock)

Returning a book mutates two rows — the loan and the book's available_copies. We lock both. Consistent lock order (loan first, then book) prevents deadlocks.

def return_loan(db: Session, loan_id: int) -> Loan:

    # Lock loan first — prevents two concurrent return attempts
    loan = db.scalars(
        select(Loan).where(Loan.id == loan_id).with_for_update()
    ).first()

    if loan is None:
        raise NotFoundError(f"Loan {loan_id} not found")
    if loan.returned_at is not None:
        raise ConflictError("This loan has already been returned")

    now = _now()
    overdue_days = max(0, (now - loan.due_date).days)
    loan.returned_at = now
    loan.status = "returned"
    loan.fine_amount = round(overdue_days * settings.FINE_PER_DAY, 2)

    # Lock book second — we're incrementing available_copies
    book = db.scalars(
        select(Book).where(Book.id == loan.book_id).with_for_update()
    ).first()
    if book is not None:
        book.available_copies = min(book.total_copies, book.available_copies + 1)

    try:
        db.commit()
    except IntegrityError:
        db.rollback()
        raise ConflictError("This loan has already been returned")

    db.refresh(loan)
    return loan

Defense in Depth — Three Layers

Three independent mechanisms guard against inventory corruption. Any one of them is sufficient; together they are very robust:

LayerMechanismWhat it catches
1. Row lock SELECT … FOR UPDATE Serializes concurrent borrows at the PostgreSQL level — the primary defense
2. IntegrityError handler except IntegrityError Any constraint violation the application logic missed — maps it to a clean 409
3. DB CHECK constraint CHECK (available_copies >= 0) Absolute last line — PostgreSQL itself rejects negative inventory even if the above two fail

Pessimistic vs Optimistic Locking

Optimistic locking (version columns + retry) is a valid alternative. The right choice depends on the conflict rate and the cost of retrying.

ApproachGood when…Bad when…
Pessimistic (FOR UPDATE) Conflicts are plausible; critical section is short (milliseconds) Lock held across a slow operation (e.g., calling an external API mid-transaction)
Optimistic (version column) Conflicts are genuinely rare; reads vastly outnumber writes High contention — frequent retries frustrate users and waste CPU

For library borrows: the critical section is pure DB work (milliseconds), and "please try again" is poor UX when the last copy is truly gone — the retry just fails again. Pessimistic locking is the right call.

Interview framing: "We use pessimistic row locking because borrow operations are fast and conflicts — though rare — are serious. Double-loaning a book is worse than a brief lock wait. We also have IntegrityError handlers as a second layer and DB-level check constraints as a third, so three independent defenses guard against inventory corruption."

Retrieval Practice

1. What does .with_for_update() add to the generated SQL?

SQLAlchemy translates select(Book).with_for_update() to SELECT … FROM books WHERE … FOR UPDATE. PostgreSQL holds a row-level exclusive lock on every matched row until the transaction commits or rolls back.

2. Why handle IntegrityError even though there is already a row lock?

The DB has a CHECK constraint available_copies >= 0. If application logic has a bug that allows a negative value, PostgreSQL rejects it with an IntegrityError. We catch it and convert it to a clean 409 instead of leaking a 500 Internal Server Error.

3. In return_loan, what is the lock acquisition order and why does it matter?

Consistent lock ordering prevents deadlocks. If Transaction A locks Loan then Book, and Transaction B tries to lock Book then Loan, they can deadlock waiting for each other. Always acquiring locks in the same sequence breaks that cycle.

4. Why is pessimistic locking better than optimistic locking for this use case?

With optimistic locking, the caller must retry when a conflict is detected. For a borrow, "try again" is poor UX — if inventory is truly exhausted, every retry fails for the same reason. Pessimistic locking queues the request and returns exactly one clear outcome: success or a 409 with an explanation.
