System Architecture Overview

The 30-second pitch, the 5-minute walkthrough, and the "why" behind every layer.

The 30-Second Pitch

This is a REST API for a neighborhood library: members borrow and return books, staff manage the catalog, and the system enforces inventory constraints atomically. It's built on a production-grade FastAPI stack — PostgreSQL for persistence, Redis for response caching, Celery for background jobs — deployed to AWS ECS Fargate via Terraform and GitHub Actions.

The Four-Layer Architecture

Every domain module — books, members, loans — follows the same pattern. Four files, strict separation of concerns:

┌──────────────────────────────────────────────────────┐ │ HTTP Request │ └───────────────────────┬──────────────────────────────┘ │ ┌─────────▼──────────┐ │ router.py │ HTTP only — routes, auth deps, status codes └─────────┬──────────┘ │ calls ┌─────────▼──────────┐ │ services.py │ Business logic — NEVER imports FastAPI └─────────┬──────────┘ │ queries/mutates ┌─────────▼──────────┐ │ models.py │ SQLAlchemy ORM — table definitions └────────────────────┘ ▲ ┌─────────┴──────────┐ │ schemas.py │ Pydantic DTOs — request/response shapes └────────────────────┘

The key invariant: services never import from FastAPI. This means the service layer is testable without an HTTP context, reusable in Celery tasks or CLI scripts, and has a single clear responsibility — business logic only.

A Request From End to End

When a staff member borrows a book, here is the exact path:

POST /api/v1/loans  { "book_id": 42, "member_id": 7 }

 1. LoggingMiddleware    — assign correlation_id, start timer
 2. CORSMiddleware       — validate Origin header
 3. JWT Dependency       — decode Bearer token → UserContext(user_id, roles)
 4. loans/router.py      — validate request body via LoanCreate Pydantic schema
 5. loans/services.py    — borrow_book(db, book_id=42, member_id=7)
 6.   SELECT FOR UPDATE  — lock book row #42 in PostgreSQL
 7.   Check copies       — available_copies >= 1?
 8.   Decrement          — available_copies -= 1
 9.   INSERT loan        — status='active', due_date = now + 14 days
10.   db.commit()        — book update + new loan commit atomically
11. 201 LoanResponse     — Pydantic serializes ORM object → JSON
12. LoggingMiddleware    — log request/response pair with execution time

Technology Choices — and Why

ChoiceAlternativeWhy this one
FastAPI Django REST Framework Auto-generated OpenAPI docs, Pydantic validation at the boundary, clean Depends() injection. DRF's magic (viewsets, mixins, serializers) fights against strict layer separation.
Sync SQLAlchemy 2.0 Async SQLAlchemy Simpler transaction reasoning. Row locking (SELECT FOR UPDATE) is natural in sync. Gunicorn + thread workers is sufficient for this workload — async adds complexity without a meaningful win.
PostgreSQL SQLite / MySQL Row-level locking, trigram GIN indexes for fuzzy search, robust ACID guarantees, managed on RDS.
Redis In-process cache Shared across all ECS tasks (multiple replicas). Survives pod restarts. TTL + eviction built-in.
HS256 JWT RS256, sessions, API keys Single service — symmetric signing is appropriate and simpler. No public key distribution needed. Stateless: no session store, no database lookup per request.
Celery Cron, APScheduler Distributed task queue with retries, beat scheduler, Flower monitoring. Overdue loan flagging is a daily idempotent job that benefits from Celery's retry semantics.

The Session Dependency — Auto-Commit and Auto-Rollback

Every route that touches the DB receives a session via db: Session = Depends(get_session). The dependency handles transaction lifecycle automatically:

def get_session() -> Generator[Session, None, None]:
    session = get_sessionmaker()()
    try:
        yield session
        session.commit()      # ← auto-commit on route success
    except Exception:
        session.rollback()    # ← auto-rollback on any exception
        raise
    finally:
        session.close()       # ← always closed

Services never call db.commit() themselves — except inside atomic operations like borrow/return where they must commit both the loan and the book update together. Everything else is committed by the dependency after the route returns successfully.

Retrieval Practice

1. What is the key rule about services.py that makes the architecture testable and reusable?

Services accept a Session and domain arguments. No FastAPI means they work identically in an HTTP route, a Celery task, a CLI script, or a unit test — no HTTP context needed.

2. Why was sync SQLAlchemy chosen instead of async SQLAlchemy?

Sync is a deliberate choice, not a limitation. One thread, one transaction, one mental model. SELECT FOR UPDATE works naturally. The workload doesn't require async — Gunicorn + thread pool handles the concurrency profile fine.

3. What does the get_session() dependency do when a route raises an exception?

The dependency wraps the session in try/except/finally: success → commit, exception → rollback, always → close. Partial writes are never committed to the database.

4. Why is HS256 JWT appropriate here, but NOT in a multi-service system?

With HS256, any service that verifies tokens must also hold the signing secret — meaning it could forge tokens. For a single service this is fine. In a multi-service system, RS256 is better: the auth service signs with a private key; other services verify with the public key only and can never forge tokens.
